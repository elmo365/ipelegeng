locating-vs-understanding rule, comments-and-memories-are-hypotheses, the evidence
standard and the pre-finding checklist. Invoke it, or read
`.claude/skills/code-discovery/SKILL.md`.

**This file is the *terrain*: the hazards specific to this repository.** The skill is
the map-reading technique; this is which parts of this particular map are wrong.

The method was extracted from a guide written for another codebase (the Auctions plugin
suite). That copy is gone — every path in it pointed at a repo that does not exist here,
and a discovery guide that sends you looking for `PLUGINS/Auctions` in a Flutter tree is
worse than none.

### Hazards specific to this tree

| Hazard | Why it bites | What to do |
|---|---|---|
| **`design/*.dc.html`** | 90–170 KB HTML canvases. They **are** greppable and that is the trap: the design's real data — `PAL`, `CATS`, `BSTATES`, `REQUIREMENTS` — lives in a `<script>` block. A flattener that stripped `<script>` once made eleven booking states look absent, and the repo was documented from the wrong reading. See [`design-deltas.md`](design-deltas.md) §14 | Extract with the script block intact. Never conclude a screen or token is missing from a canvas without checking the `<script>` |
| **`app/build/`** | Holds gate screenshots and build artifacts, including copies of compiled Dart | Never a source of truth. Ignore every hit |
| **Generated Dart** | `lib/firebase_options.dart` is generated by `flutterfire configure`; `*.g.dart` if any appear | Real hits, meaningless as intent. Never cite as a decision |
| **`app/test/` mirrors `app/lib/`** | A symbol name usually matches in both | Check the path before quoting — a test's expectation is not the implementation |
| **Two constants, one meaning** | `Session.codeLength` and `VerifyScreen.codeLength` were both `4`, declared separately, and drifted apart in intent. §21.1 | When a value looks duplicated, check whether one aliases the other before changing either |
| **Docs outnumber code** | 30+ files in `docs/`. A grep for a behaviour will hit prose describing it, often prose describing what it *should* be | A doc is a claim about the code, at the standing of a comment. Check it |

### The evidence standard here

`test-strategy.md` names the three sources that must agree for a user-facing claim, and
adds the UI corollary this repo learned the hard way: **compare a screenshot to its
artboard element by element, never as a whole.** The gate at
`app/integration_test/gate_test.dart` produces the screenshots; a whole-screen glance
passed a flat-white wordmark that was plainly visible in the image.
