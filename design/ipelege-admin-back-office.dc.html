Ipelege · back office
The other half of the product
Four of the five flows that wait on a human here move money or gate income. A provider in PENDING earns nothing, an unmatched EFT deposit is the failure most likely to lose a provider permanently, and a reversal under review has no exit without someone deciding it. So this is designed as a set of queues with owners and ages, not as a CRUD tree.

What this surface is
Decided 2026-08-17: Django admin inside the same modular monolith, on /staff/*. Not a bespoke web app, and explicitly not Flutter Web. That decision sets the design brief — the framework already supplies the furniture, so the work here is density, queue framing, and the shape of a decision.
table_rows
Dense reading, not a canvas
Back-office work is tabular reading, keyboard-driven queues, document inspection and audited writes. Server-rendered HTML does text selection, find-in-page and printing for free. A canvas renderer does none of them well.
hub
One domain layer, two entry points
Every admin write calls the same service function the API calls. An admin approving a category and an automatic approval must produce byte-identical state transitions and audit rows.
gavel
The rule that keeps it honest
No admin surface may write to a field where a state transition exists for it. Status is read-only text; the transitions are named actions with a reason. A dropdown is an unaudited second implementation of the state machine.
Interface standards for the back office
The phone system optimises for one thumb on a 360dp screen. This surface optimises for a reviewer with a keyboard, a 1440px window and forty documents to get through before lunch. Almost every mobile token is wrong here, so the admin has its own small set.
